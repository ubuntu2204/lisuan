# 仓库组织约定

## 一、与本项目相关的文件，一律放进本仓库

排查过程中产生的脚本、源码、配置、工具，只要属于这个项目，
就应移入 `~/project/lisuan/` 下的对应主题目录，不要留在 home 或其它位置。

**理由**：散落在 home 的文件没有版本控制，丢失即不可恢复。
2026-08-31 排查时发现 `~/mm_patch`（237MB）与 `~/gf-compat`（34MB）
完全未入库，其中含关键补丁源码与整个开发工作目录——一旦磁盘出问题就全没了。

已按此执行的例子：

- `~/gf-compat` → `minion-masters/gf-compat/`
- `~/mm_patch`  → `minion-masters/mm-patch/`

主题目录对应：`steam/` `dkms/` `mesa/` `minion-masters/` `underlords/` `electron/` `audio/`。

## 二、不能开源的：不跟踪，但必须在文档注明获取方式

以下类别**不得提交进 git**，用 `.gitignore` 排除：

| 类别 | 例子 |
|---|---|
| 厂商专有二进制 / 源码 | `libSC.so`、`libvulkan_gf.so`、`lisuangpu-*.deb`、解包的厂商 DKMS 源码树 |
| 反编译 / 逆向产物 | 游戏反编译出的程序集、IL2CPP 互操作 DLL、反汇编与 dump 结果 |
| 第三方大体积依赖 | BepInEx / Il2CppInterop / dotnet 运行时（百 MB 级） |
| 针对闭源软件的改动 | 对专有驱动的补丁、hook、绕过手段的二进制产物 |

**排除 ≠ 丢弃**：文件仍保留在仓库目录内供运行时加载，
但**必须**在对应目录的 README 中写清三件事：

1. 它是什么、做什么用
2. 为什么不能入库
3. 从哪里能获取——具体路径、包名或官方来源

现有范例（照此格式写）：

- `minion-masters/gf-compat/README.md` →「厂商专有二进制」章节
- `minion-masters/assets-mm-gf-vulkan/README.md` →「MMPatch 权威版本与两个陷阱」章节
  （原为 `mm-patch/README.md` 的「第三方依赖」章节；`mm-patch/` 已于 2026-08-31 删除，git 历史可查）

## 三、历史文档里的路径不逐处改写

排查记录类文档（如 `MinionMasters-攻坚全记录.md`）保留当时的原始路径，
只在文首加一段「路径说明」给出新旧对应关系。

理由：这类文档的价值在于如实记录排查现场，逐处改写会削弱其可信度，
也容易改错。**操作指南类**文档（如 `fix-minion-masters.md`）则相反，
必须保持路径最新，因为读者会直接照抄。

## 四、改动后自查

涉及目录移动 / 重命名时：

1. 全局搜索旧路径，确认无遗漏引用（含脚本、文档、Steam 配置等外部配置）
2. 检查 `.gitignore` 是否误伤需要入库的文件
3. 跑 `bash tests/run-tests.sh`（7 个套件）
4. 注意 git 不保留 mtime，**不要写依赖文件新旧比较的逻辑**
