# 11 对战平台启动排障约定

适用对象：`11/`，Proton 11.0 的 wine-11.0。现行前缀为正式版
`~/.deepinwine/11duizhan-263`；3.0 公测版历史前缀为 `~/.deepinwine/11duizhan-wine11`。
记录日期：2026-11-19。本文是排障约定与证据索引；操作指南以 `11/README.md` 为准。

## -1. 现行方案：官网正式版 2.6.3.48（先用它，不要重做 3.0 的坑）

- 网上成功案例与本机实测都指向**官网正式版 2.6.3.x**，不是本机此前安装的 `3.0.0.68` 公测版。
  正式版主程序为 `11Loader.exe`（大写 L）+ `bins/11Client.exe`；3.0 公测版为 `11loader.exe`
  + `yybins/YYClient.exe`，两者问题完全不同。
- 安装包：`go.5211game.com/?id=10` → `download.5211game.com/11/download/5211Setup_2.6.3.48.exe`；
  需 `Referer: https://www.5211game.com/`，SHA256
  `20066c97cfcf25b80cbf7b48d89f2d1508a11783978a3a201bd6fabff46a23b8`。
- 安装/启动/桌面脚本已默认前缀 `~/.deepinwine/11duizhan-263` 并兼容大小写主程序名。
  正式版无需 `fix-11-stack.sh`、`fix-11-gdi.sh`、winetricks 或纯 32 位前缀。
- 验收基线：`./11/run-11duizhan.sh` 单次启动，t=10s / 25s 窗口可见；
  `stack overflow` 0、`out of GDI object handles` 0、`Unhandled exception` 0，
  GDI 句柄峰值 142。登录/进房间/联机仍未验收，不得写成「平台可用」。
- 下面第 1–5 节是 **3.0 公测版遗留排障记录**，仅当显式切回旧前缀时适用。

## 0. 原则

- **已修与未修必须分开写**。窗口出现、越过栈溢出、版本冻结都不是「平台可用」。
- 禁止看门狗、自动重启、守护、存活监控、重试循环（见 `崩溃处理约定.md`）。
- 允许「绕过」但必须如实标注：例如 `-updatemode=0` 是绕开 Wine 下失效的厂商更新器，
  不是修好更新器；自更新/重装后必须重跑栈补丁。
- 厂商 exe、DLL 只改本机前缀内的副本；改前备份，`--status` / `--uninstall` 必须可用。
- 取证顺序：应用日志 → Wine `WINEDEBUG` → PE 栈字段/导入表 → gdb/句柄计数。
  不要先用「多试几次」代替定位。

## 1. 已确认的分层结论

| 层 | 现象 | 根因 | 处置 | 状态 |
|---|---|---|---|---|
| 桌面/合成 | 图标点击后 `wmctrl -l` 有窗口但合成图全无 | 主窗口 Depth 32/ARGB 在 Wayland/XWayland 下不可见 | `run-11duizhan.sh` 注入 `XLIB_SKIP_ARGB_VISUALS=1`（`E11_SKIP_ARGB_VISUALS=0` 可 A/B） | 已修 |
| 启动崩溃 | `stack overflow 3008 bytes addr 0x48de11`（3.0.0.68）/ `0x48e441`（3.0.0.79） | 真正客户端是 `yybins/YYClient.exe`，不是 `11loader.exe`；其频道序列化递归帧约 4KB，PE 栈保留仅 1MB | `fix-11-stack.sh` 把 YYClient + 11loader 栈保留改 16MB、提交 64KB | 已修（但会被自更新冲掉） |
| 版本稳定 | 两次启动间 3.0.0.68 ↔ 3.0.0.79 来回切换，`YYUpdate.log` 每次走 `Check→Download→Install→Final` | 厂商更新器在 Wine 下状态不稳；新 exe 覆盖 PE 栈补丁 | `run-11duizhan.sh` 无参数默认追加 `-updatemode=0`；`E11_ALLOW_UPDATE=1` 恢复 | 已绕过，非修复 |
| 运行期退出 | 约 12 秒后 `platform.ini error_code=1 / Unhandled exception`，libcef 报 `0x80000003` | Wine 11 GDI 句柄表 65536 耗尽；每轮泄漏 1 DC + 1 FONT + 4 REGION | **未修复** | 当前阻塞点 |

`fix-11-stack.sh` 用「忽略两个栈 DWORD 的 SHA256」识别 exe 版本：版本变化时旧备份转存
为 `.orig.<hash8>`，再备份当前版本，避免 `--uninstall` 还原成旧版本。自更新/重装后
必须重跑：`./11/fix-11-stack.sh && ./11/fix-11-stack.sh --status`。

## 2. GDI 泄漏的硬证据（2026-11-19，冻结版本后仍成立）

单次 `E11_WINEDEBUG='+err,+gdi,+seh' ./11/run-11duizhan.sh`：

- `thread 0144`（YYClient，日志中有 `[qflogin] attach!` / `[IPCProxy] attach!`）分配/释放计数：
  - `NTGDI_OBJ_REGION`：138927 分配 / 95302 释放 → 净漏 43625；
  - `NTGDI_OBJ_FONT`：48169 / 37248 → 净漏 10921；
  - `NTGDI_OBJ_DC`：10910 / 2 → 净漏 10908；
  - `NTGDI_OBJ_MEMDC` 117 / 116，不是主要泄漏对象。
- 峰值句柄数到 65503/65536；`err:gdi:alloc_gdi_handle out of GDI object handles, expect a crash`
  出现 5 次；随后 `yybins/log/<时间>/err.log` 记 `Error Module: ...\cef\libcef.dll`、
  `Code: 0x80000003`、`Addr: 0x719fc9dd`，并落 `YYClient_*.dmp`。
- 对象类型可从 Wine 的 `alloc_gdi_handle` 第二个入参识别：`0x10000`→`NTGDI_OBJ_DC`
  （显示 DC，来自 `NtGdiOpenDCW`），`0x410000`→`NTGDI_OBJ_MEMDC`
  （来自 `NtGdiCreateCompatibleDC`），`0x40000`→REGION，`0xa0000`→FONT。
  **泄漏的是显示 DC，不是 CompatibleDC。**
- 冻结版本后仍复现 GDI 耗尽；之前「冻结后未见表耗尽」的说法不成立（那次采样漏看
  `+gdi` 计数），不得据此宣称 GDI 问题消失。

## 3. 已证伪/失败方向（不要重做，除非有新证据）

1. **归错进程**：把 `0x48de11` 归到 `11loader.exe` 并改它的栈，客户端仍溢出。
   `11loader.exe` 只是拉起器，真正进程是 `YYClient.exe`。
2. **CEF/Qt 表面开关**：`--disable-gpu` / SwiftShader、`QT_OPENGL=software|desktop`、
   Wine 虚拟桌面、Proton 8、全新前缀、软件 GL 三件套，均不能解决黑屏、栈溢出或 GDI 泄漏。
3. **模拟 Windows GDI 配额**：把 `win32u.so` 的 `alloc_gdi_handle` 上限从 65536 改成
   10000（VMA `0x9fc0c` 的 `add $0x180000,%eax`）虽生效，但客户端更早崩溃（约 10 秒）。
   应用不能容忍句柄表满后的 NULL；这不是修复，已移除该垫片。
4. **LD_PRELOAD 拦截 `NtUserGetDC`**：写了 32 位探针导出同名符号，运行期 **0 命中**。
   Wine 的 syscall dispatcher 走内部函数指针/表，不是按动态符号查找；按名 interpose 无效。
   同理不要仅凭 `nm -D win32u.so` 有 `NtGdi*` 就断言可 LD_PRELOAD。
5. **user32 PE wrapper + `WINEDLLOVERRIDES=user32=n[,b]`**：
   - 32 位 wrapper 放在 `syswow64/user32.dll` 时只拦到 `11loader.exe` 的 5 次 GetDC；
     `YYClient.exe` 仍加载 Proton 内置 `lib/wine/i386-windows/user32.dll`（known DLL 优先），
     因此没拿到泄漏调用点。
   - 用 mingw 编译必须加 `-static-libgcc`，否则报缺 `libgcc_s_dw2-1.dll`（c0000135）。
   - 相关文件 `11/fix-11-gdi.sh`、`11/gen-11-user32-def.py`、`11/user32-gdi-wrapper.c`
     **当前只是诊断件，不是修复**；`E11_GDI_WRAP=1` 只能作为 A/B 开关。
6. **gdb**：`ptrace_scope` 阻止 attach 已运行进程；从 gdb 启动则需显式
   `handle SIGUSR1/SIGUSR2/SIGCHLD/SIGPIPE/SIGALRM nostop noprint pass`，否则 Wine 的信号
   会让 gdb 停住。跨 `__wine_syscall_dispatcher` 的 `bt` 帧不可靠（曾把栈上垃圾解析成
   `libLLVM.so` / `IM.dll!GetKitInterface`），不能作为调用者结论。
7. **把版本冻结当成修好**：`-updatemode=0` 只解决反复换 exe/冲掉栈补丁；
   GDI 泄漏在冻结版本上仍复现。
8. **纯 32 位 Wine 前缀**：用 Proton wine 建 `WINEARCH=win32` 前缀并复制 3.0 公测版，
   仍复现 GDI 耗尽（5 次、峰值 65503/65536）。前缀架构不是根因。
9. **winetricks 原生运行库**：在同前缀装 `mfc42/msxml3/vcrun2019`（`corefonts` 下载失败）
   后，3.0 公测版仍复现 GDI 耗尽。缺少这些运行库不是根因。
10. **网上成功帖的迷惑点**：成功案例没给出 Wine 版本号，但用的是官网正式版 2.6.3.x；
    不要把它解读成「同一份 3.0 公测版换个 Wine 参数就能跑」。

## 4. 当前下一步（未完成，需先取证再改）

- `YYClient.exe` 的导入表把 `GetDC`/`ReleaseDC` 从 `USER32.dll` 引入。本次解析该文件
  offset `0x7319ea` 是 `USER32.dll\0`，与等长 `e11gdi.dll\0` 可直接原地替换（**版本变化后
  必须重新解析导入表，不能盲写偏移**）。
- 候选做法：在 `yybins/` 放 `e11gdi.dll` + `user32_orig.dll`（内置 user32 重命名副本），
  把 YYClient 的 USER32 导入重定向到 `e11gdi.dll`，使包装层真正进入客户端进程，再抓
  GetDC 调用者；确认后才有依据做 DC 回收或定点 patch。
- `11/gen-11-user32-def.py` 已支持第三个参数指定库名（默认 `user32`），但
  `11/fix-11-gdi.sh` 仍按 `user32.dll` 覆盖前缀 syswow64；IAT 方案尚未实现，勿误认为已交付。
- 任何 DC 回收都必须限定在目标进程、可关闭、可回滚；不得常驻监控或崩溃后自动拉起。

## 5. 验收口径

- 栈：`fix-11-stack.sh --status` 两个 exe 均为 16MB/64KB；`stack overflow` 计数为 0。
- 版本：`Config/yyclientx.xml` 与 `gamever.ini` 在一次运行前后不变。
- GDI：`+gdi` 日志 `out of GDI object handles` 为 0，净泄漏对象为 0 或可解释；
  `err.log` 无 `0x80000003`；`platform.ini normal_exit=1`。
- 窗口：`wmctrl -lpG` 可见，`xwininfo` 为 `IsViewable`；合成画面按
  `Wayland抓图约定.md` 取证，不用 xwd 黑屏当渲染故障证据。
- 登录、进房间、War3 联机尚未验收；不得写成「平台可用」。
