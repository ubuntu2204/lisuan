# 《求生之路 2》探索记录（L4D2 on 砺算 7G100）

> 本文件记录截至 **2026-10-25 14:52** 的完整探索与修复状态，供后续复查与回归验证。
> 当前结论：**原生 32 位 L4D2 已可在砺算 7G100 上全 GPU 硬件渲染稳定游玩，D16 手电筒阴影也已恢复。**

---

## 一、当前结论

- 链路：`hl2_linux`（32 位原生）→ `shaderapivk.so`（DXVK v2.0）→ `libvulkan_virtio.so`（32 位 Venus 客户端）→ Unix socket → `virgl_test_server --venus`（64 位私有构建）→ `libvulkan_gf.so` → 7G100。
- 已修复当前唯一阻塞：**D16 深度纹理因 `VK_IMAGE_USAGE_ATTACHMENT_FEEDBACK_LOOP_BIT_EXT` 被 gf 拒绝，导致 DXVK 资源创建失败、游戏在 `MatQueue0` 线程 SIGSEGV**。
- 修复方式：**私有 Venus 服务端不向客户端暴露 `VK_EXT_attachment_feedback_loop_layout`**，使 DXVK 回退到正常的 `0x27` usage 组合。
- 实测：
  - `r_flashlightdepthtexture 0` 场景下稳定进入实际地图。
  - `r_flashlightdepthtexture 1` 场景下同样稳定，D16 错误为 0。
  - 未再观察到 `MatQueue0` 的 SIGSEGV。
- 旧的「启动器强制 `+r_flashlightdepthtexture 0`」规避已移除；用户可自行传 `+r_flashlightdepthtexture 0` 或 `1` 覆盖。

---

## 二、根因链

### 1. 崩溃现场
- GDB 日志显示崩溃线程为 **`MatQueue0`**，栈顶位于 `bin/shaderapivk.so`。
- 崩溃点附近寄存器中 `ebx=0xffffffff`，说明在解引用一个无效句柄/索引。
- 同一次日志中仍出现 3 条：

  ```text
  D3D9: Cannot create texture:
    Format:  D3D9Format::D16
    Extent:  200x200x1
    Usage:   2
  ```

  说明当时 D16 失败仍存在，只是不一定是 400x400 的手电筒阴影路径。

### 2. 关键发现：失败发生在 `vkCreateImage` 之前
DXVK v2.0 的 `D3D9CommonTexture::CreatePrimaryImage()` 在真正调用 `vkCreateImage` 前会先调用 `vkGetPhysicalDeviceImageFormatProperties2()` 检查能力；若失败就直接抛 `Cannot create texture`，**旧 `vkCreateImage` shim 永远拦不到**。

### 3. 真正触发条件：feedback-loop usage
原生 64 位 gf 驱动实测：

| D16 usage | 结果 |
|---|---|
| `0x20`（DEPTH_STENCIL_ATTACHMENT） | 成功 |
| `0x24`（+SAMPLED） | 成功 |
| `0x27`（+TRANSFER_SRC/TRANSFER_DST） | 成功 |
| `0x80027`（+ATTACHMENT_FEEDBACK_LOOP） | **失败，`VK_ERROR_FORMAT_NOT_SUPPORTED (-11)`** |

其他深度格式（D24S8、D32F 等）同样受影响。

DXVK v2.0 会给 D3D9 的深度纹理附加 `VK_IMAGE_USAGE_ATTACHMENT_FEEDBACK_LOOP_BIT_EXT`，但 gf 驱动虽然上报支持 `VK_EXT_attachment_feedback_loop_layout`，实际对带该 usage 的深度图却直接拒绝，造成 DXVK 以为格式不可用。

## 三、修复

### 1. 私有 Venus 服务端屏蔽有问题的扩展
在 `src/venus/vkr_common.c` 中把：

```c
.EXT_attachment_feedback_loop_layout = true,
```

改为：

```c
/* gf advertises this extension but rejects depth images carrying the
 * corresponding usage bit. Hide it from DXVK in this private bridge.
 */
.EXT_attachment_feedback_loop_layout = false,
```

这样 DXVK 不会看到该扩展，也就不会往 D16 深度纹理加 `0x80000` usage 位。系统 gf 驱动、其他游戏均不受影响，只影响本目录私有 `virgl_test_server`。

### 2. 构建脚本支持多补丁
`vtest-forward/build-venus-bridge.sh` 已改为按顺序应用 `patches/*.patch`，避免后续新增兼容补丁时被旧逻辑覆盖。

### 3. 修复脚本自动识别补丁更新
`fix-l4d2.sh` 的 `build_server()` 现在会根据 `build-venus-bridge.sh` 和 `patches/*.patch` 的内容哈希判断是否需要重建服务端，避免「补丁已改但二进制未重建」的静默失效。

## 四、验证记录

### 1. 扩展屏蔽生效
DXVK 日志中：

```text
VK_EXT_attachment_feedback_loop_layout
  attachmentFeedbackLoopLayout           : 0
```

且不在 `Enabled device extensions` 列表中，说明私有服务端确实没有把该扩展暴露给客户端。

### 2. 实战路径验证
- 启动 `+map c1m1_hotel`，从主菜单进入战役加载页，再到实际游戏场景。
- 连续观察约 2 分 25 秒，未出现 SIGSEGV。
- 同样开启 `r_flashlightdepthtexture 1` 后再次进入实际场景，D16 错误仍为 0。
- 原崩溃点已越过，不再复现。

### 3. 旧错误清理
- 旧的 `vk32-depth-test.c` / `vk32-scan.sh` 中深度 usage 位值写错，已纠正。
- `vkcreateimage-shim.c` 保留为诊断工具，但不再作为修复方案；正常启动不注入。

## 六、已知注意事项

1. **启动时可能仍出现一次 `SetLocale('en_US.UTF-8') failed` 警告框**
   这是 Valve Source 引擎已知问题，点 OK 即可，与本次修复无关。默认已加 `-novid` 减少触发。
2. **必须确保 Venus 服务端是新二进制**
   若不确定，可重跑：

   ```bash
   bash fix-l4d2.sh
   ```

   新脚本会自动判断补丁是否更新并重建。
3. **不要再用旧的 `vkcreateimage-shim.so` 作为修复手段**
   它无法拦住 `vkCreateImage` 之前的能力检查，且格式降级链存在风险。仅作诊断。
4. **不要把私有 Venus 补丁误当系统驱动改动**
   它只影响本目录构建的服务端，不改 `/usr/lib/.../libvulkan_gf.so`。
